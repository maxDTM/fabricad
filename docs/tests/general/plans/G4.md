# G4 fix plan: sketch solver, sketch tools, profiles, typed entry

Status: plan only, nothing implemented yet. Source: round1/advanced-sketch.md and its screenshots, plus a read of the code (line numbers as of 2026-10-22 07:05).
New tests go in `src/sketch/tests/` (test_solver, test_tools, test_curve_tools, test_sketch_ops, test_feature). Build with -j2.

## SK-01 (high): dragging or dimensioning an ellipse centre distorts the ellipse
- **Root cause**
  - The GCS ellipse is stored as an absolute centre, focus1 and radmin (`SketchSolver.cpp:196-208`).
  - `addDrag()` (`SketchSolver.cpp:783-793`) pulls only the centre when a point ref is dragged. Focus1 stays where it was, so the major axis length and angle change.
  - A driving dimension on the centre (P2P distance, `SketchSolver.cpp:581-585`) has the same problem: the Newton step moves only the centre.
- **Fix**
  1. In `addDrag()`, when the ref is `Center` of an Ellipse or EllipseArc, also pull focus1 by `d.delta`. For an EllipseArc, also pull start and end by the same delta. This mirrors the whole-curve case at lines 811-818.
  2. In `run()` when there is no drag, and when a drag does not target that ellipse's shape, add soft "keep shape" constraints for each ellipse.
     - Each constraint is tagged `GCS::DefaultTemporaryConstraint`: `addConstraintDifference(center.x, focus1.x, value(dx))`, the same for y, and `radmin == value(b)`.
     - GCS already treats tag < 0 constraints as a soft subsystem solved by SQP (`planegcs/GCS.cpp:1857-1875, 1923`) and leaves them out of DOF and conflict diagnosis (`GCS.cpp:570`).
- **Possible effects and how to avoid them**
  - SQP may converge differently from DogLeg. If the solve fails, retry once without the soft constraints and keep the current LM fallback.
  - The soft constraints must not resist intended reshaping, such as an Equal constraint between ellipses or a future major/minor dimension (SK-06). They are soft, so hard constraints still win. Add a test where a dimension changes the minor radius and the solve still succeeds.
  - DOF counts and the "fully constrained" colouring must not change. Assert the dofs in test_solver before and after.
  - Every solve with ellipses gets slower. Only ellipse slots are added, so the cost is negligible.
  - Tests to add: drag the centre and check that a, b and the angle are unchanged; dimension centre-to-centre to 30 and check the same.

## SK-02 (medium): point-to-point dimension negative and flips the geometry when edited
- **Root cause**
  - The dimension the tester placed was DistanceX or DistanceY, chosen by `linearTypeFor` (`ModifyTools.cpp:1066-1080`).
  - `Sketch::measure` returns a signed `pb.x - pa.x` (`Sketch.cpp:238-243`). `place()` stores that sign without normalising it; the Angle case is normalised at `ModifyTools.cpp:1157`.
  - The label shows -40.52. Typing 30 drives +30, so the geometry jumps to the other side.
- **Fix**
  1. In `DimensionTool::place()`, for a two-point DistanceX or DistanceY with value < 0, swap a and b and negate the value, the same way Angle is handled.
  2. In `SketchSession::dimensionText` (`SketchSession.cpp:587`), display |value| for DistanceX and DistanceY.
  3. In `applyDimensionText` (`ModifyTools.cpp:46`), for DistanceX and DistanceY with an old value < 0 and a positive typed value, keep the old sign. This covers old files and the signed `@dx,dy` dimensions from `CreateTools.cpp:506`.
  4. `dimensionEditText` should show |value|.
- **Possible effects and how to avoid them**
  - Single-point coordinate dimensions (point to origin, signed X or Y) are legitimately signed. Leave them signed, but display the absolute value only if the side is shown by placement. Otherwise keep the sign for coordinates; decide during review.
  - `test_solver.cpp:194` uses -7 on purpose. The solver semantics do not change, so do not touch `SketchSolver.cpp:612-627`.
  - Check `test_tools.cpp:587-598` and `test_tools.cpp:895` for value-sign asserts.
  - Expressions bound to a negative value (`d1 = -x`): apply the sign rule only to numeric input.

## SK-03 (medium): Trim does nothing on a spline; Break on a spline says "Cannot break here"
- **Root cause**
  - `computeBracket` (`Sketch.cpp:565-570`) only allows removing a spline whole. When anything crosses it, `trim()` returns unchanged (`Sketch.cpp:676`) with no message.
  - `trimPiece` returns nullopt (`Sketch.cpp:656`), so there is no preview.
  - `Sketch::split` (`Sketch.cpp:1503`) accepts only Line and Arc.
- **Fix**
  1. Add `BSpline2 split/subrange(lo, hi)` in `SketchCurves.cpp`, using knot insertion to full multiplicity.
  2. Treat splines like lines in `computeBracket`: parameter range [u0, u1], with hits from `paramOf`.
  3. Add a spline branch to `trimPiece`, `trim` and `split`.
     - Control-point Spline: exact pieces.
     - FitSpline: keep the fit points inside the range plus the cut point. Keep their original parameters in `knots` so the solver's `addFitRules` (`SketchSolver.cpp:243`) reproduces nearly the same shape.
     - Remap Vertex-indexed constraints (`redistributeConstraints` and `dropPointConstraints` need Vertex index support).
  4. When trim finds no piece, show "Cannot trim this curve" instead of failing silently.
- **Possible effects and how to avoid them**
  - Vertex-index constraints on the new piece could point at the wrong fit point. Add tests in test_sketch_ops: trim a spline crossed by a line, then check the vertex count, the end coincidence and that the solve succeeds.
  - Closed (start == end) splines need the closed-curve branch: two cuts required.
  - Text keeps the whole-only behaviour.
  - Power-trim drag (`TrimTool::mouseMove`) must not delete a spline piece by piece on every move. It already trims each piece once, but verify.

## SK-04 (medium): fit-point spline closed on its first point is not closed
- **Root cause**
  - `SplineTool::complete()` (`CurveTools.cpp:344-347`) and `finishSpline` (line 371) treat the spline as closed only when the last click is exactly (1e-9) on the first point.
  - Inference does not snap to the in-progress spline's own first point, which is not sketch geometry yet. The click lands near it, and the curve stays open with no coincident.
- **Fix**
  1. In SplineTool, override inference: when there are 3 or more points and the cursor is within `tol(c)` of `pts_.front()`, snap exactly to it and show the point marker. The click then completes the spline.
  2. Optionally add a Tangent constraint between End and Start (the solver supports spline end tangency, `SketchSolver.cpp:702`) so the closure is smooth, as in Fusion.
- **Possible effects and how to avoid them**
  - Profile detection must accept a single closed spline loop. `computeProfiles` uses the OCC splitter; add a test_feature assert of 1 region.
  - A tangent closure may make the solver fail for degenerate 3-point splines. Make it a soft option, or skip it below 4 points.
  - Control-point splines share `complete()`. Keep the same behaviour (closing the control polygon) but do not add the tangent there.

## SK-05 (medium): offset of an ellipse produces no geometry
- **Root cause**
  - `Sketch::offset` keeps only Line and circular curves (`Sketch.cpp:956-957`).
  - `offsetCurve` returns nullopt for Ellipse, EllipseArc and Spline (`Sketch.cpp:894-897`).
  - The tool message comes from `ModifyTools.cpp:597`.
- **Fix**
  1. In `offsetCurve`, approximate the offset of Ellipse, EllipseArc and Spline with a FitSpline. Sample about 48-64 points along the curve, offset each by d along the normal, and make the result closed (coincident) for a full ellipse. Alternatively, use an OCC `Geom_OffsetCurve` plus a `GeomConvert` approximation into a control Spline.
  2. Extend `sideOfCurve` and `runIsClosed`/`runPolyline` to these types.
  3. Corner trimming between chain items (`Sketch.cpp:995-1010`) only handles lines and circles. For spline offsets, use `intersectPolylines`, or skip corner trimming.
- **Possible effects and how to avoid them**
  - `Sketch.cpp:1225` (fillet centre candidates) dereferences `offsetCurve(...)` without checking. Make sure its callers still pass only lines and circles, or guard the dereference.
  - No offset dimension is added for curved results; the message at `ModifyTools.cpp:618` already covers that.
  - A self-intersecting inward offset of a thin ellipse (d > minor radius of curvature) gives a bad curve. Return nullopt when d ≥ b²/a on the inside.

## SK-06 (medium): an ellipse cannot be dimensioned; second-entity picks are silently ignored
- **Root cause**
  - `DimensionTool::candidate()` maps any non-line, non-circle curve to Radius (`ModifyTools.cpp:1090-1093`). `measure()` returns nullopt for an ellipse, which produces "Cannot measure that combination".
  - Pairs only promote circular curves to their centre (lines 1102-1103).
  - The sketch origin and the origin axes are not sketch geometry, so `sk->hit` misses them. `mousePress` (lines 929-944) then does nothing and shows no message.
- **Fix**
  1. Add ellipse major and minor radius dimensions. Either add new types (MajorRadius/MinorRadius, also registered in the `SketchGeometry.cpp:140` type list and JSON), or use Radius with a sub-flag; the new types are clearer.
     - Minor: `addConstraintEqual(radmin, value)`.
     - Major: two auxiliary points with `addConstraintInternalAlignmentEllipseMajorDiameter` plus a P2P distance of 2a.
     - Pick the major or minor dimension from the label position relative to the axes.
  2. Promote an elliptical curve to its centre when paired, as circles are.
  3. Origin as a pick target:
     - Point to origin: give the existing single-point DistanceX/DistanceY coordinate form for horizontal or vertical placement.
     - Aligned distance: use a fixed hidden construction point at the origin. Reuse the `kOriginFixName` Fix pattern from `SketchInference.cpp:285-287`.
     - Origin axes: a shared helper creates or reuses a fixed construction line on the axis (also used by SK-10).
  4. Any pick that is ignored, or a combination that cannot be measured, shows a status message instead of silently returning.
- **Possible effects and how to avoid them**
  - New constraint types change the file format. Older builds would fail on them; the `fromJson` of unknown types must fail gracefully.
  - Solver DOF counting for the auxiliary points: the auxiliary points must be added to unknowns and fully determined by the alignment constraints.
  - Hidden origin construction geometry shows up in the browser and selection. Mark it projected or blocked and exclude it from Ctrl+A (`SketchModeTools.cpp:511` already skips projected geometry).
  - The SK-01 soft shape constraints must not fight these dimensions (they are soft; covered by a test).

## SK-07 (medium): a polygon's construction circle splits the polygon into extra profiles
- **Root cause (not confirmed)**
  - The polygon circle is created with `construction = true` (`CreateTools.cpp:1266-1268`). `computeProfiles` skips construction geometry (`SketchProfiles.cpp:241`). `SketchFeature::profiles()` and `profileFace()` use only those regions.
  - The construction flag round-trips through JSON (`SketchGeometry.cpp:1221/1250`).
  - Screenshots 124 and 125 show the disc lighter than the corners on every polygon, which looks like overlapping translucent faces rather than separate regions. Suspects:
    - stale or duplicated profile items in the `viewer/SceneModel.cpp:257-283` cache, keyed on an outputShape hash that includes construction edges;
    - the construction circle being drawn over the profile face.
- **Fix**
  1. Reproduce headlessly first: in test_feature or test_tools, create a circumscribed polygon with the tool, finish the sketch, and assert `regions().size() == 1`.
  2. If the test passes, the defect is in the display layer. Hand it to G3 (viewer display / PART-03 profile picking) with the evidence.
  3. If the test fails, find the path that drops the construction flag (asCreated, transform or copy) and fix it in G4.
- **Possible effects and how to avoid them**
  - Overlaps G3 PART-03 and ADVANCED-SKETCH-8 (Extrude picking all profiles). Do not edit SceneModel or Selectors from G4 without agreeing it with G3.

## SK-08 (medium): viewport typed entry ignored in Ellipse, Pattern, Scale, Chamfer and Text prompts
- **Root cause**
  - These tools have no `defineValues` fields.
  - ClickTool (`CurveTools.cpp:46-150`) handles typed numbers only through `commandLineInput`.
  - The SelectFirstTool stages in TransformTools and `ChamferTool` (`TransformTools.cpp:563`) parse only command-line text.
  - `SketchTool::keyPress` (`SketchToolBase.cpp:323`) therefore returns false for digits, and letters fall through to the shortcut router.
- **Fix**
  - Add `defineValues` fields with anchors fed from `mouseMove`, `commitValues` and `typedValuesToBoxes`, as Line, Circle and Polygon do.
    - Ellipse: major radius, minor radius, angle.
    - Elliptical arc: plus sweep.
    - Rect pattern: count1, spacing1, count2, spacing2.
    - Circ pattern: count, angle.
    - Scale: factor.
    - Chamfer: distance (d1, d2).
  - TextTool: forward printable keys to the dialog Text field (like `forwardValueKey`) and consume them.
- **Possible effects and how to avoid them**
  - Letters typed before any value still act as shortcuts, which matches Fusion. Once a box is being typed into, ValueInputModel consumes the letters for expressions.
  - CommandLine and ShortcutRouter belong to G2 (APP-06..08). Do not edit them: everything stays inside the tool's `keyPress`, and the router only sees keys the tool did not consume.
  - Enter semantics: `commitValues` must return false when the stage cannot commit, so the existing accept/Enter-applies path still works (also relevant to ADVANCED-SKETCH-10, owned by G2).
  - Existing command-line argument tests (pattern "3,40", scale 1.5) must still pass. Keep the `commandLineInput` paths and route them through `typedValuesToBoxes` only when boxes are visible.

## SK-09 (low): Text dialog field ignored when text was typed in the command box; overstruck preview
- **Root cause**
  - `commandLineInput` sets `text_` (`CurveTools.cpp:483-496`) but never refreshes the dialog. The dialog's QLineEdit was created with the old `text_` (`CurveTools.cpp:427-431`), so the two sources disagree.
  - The dialog edit has no `returnPressed` handler, so Enter goes to the command line or repeats the command and re-submits the earlier text.
  - The overstruck preview comes from a stale temporary preview: `refreshPreview` runs from both the dialog lambdas and `mouseMove`, and the anchor/cursor previews overlap.
- **Fix**
  1. Make `text_` the single source: after command-line text, call `ctx.host->refreshToolDialog()` so the field shows it.
  2. Connect the edit's `returnPressed` to place or create with the edit's text.
  3. Clear all temporary previews and the dynamic text in `refreshPreview`, and draw only one preview.
- **Possible effects and how to avoid them**
  - The dialog lambdas capture `this`. A rebuild on `refreshToolDialog` must not leave stale connections; use a QPointer or the dialog's lifetime as context.
  - The "Hello via cmd box" flow tested OK. Keep the test.

## SK-10 (low): origin axes cannot be picked as the mirror line
- **Root cause**
  - `MirrorTool` only accepts `hitCurve` on a Line (`ModifyTools.cpp:667-700`).
  - The origin axes are not sketch geometry.
- **Fix**
  1. When nothing is hit and the cursor is within tol of the sketch X or Y axis (axes visible), use the axis.
  2. Without constraints, call the existing `Sketch::mirror(ids, a, d)` overload (`Sketch.cpp:1082`).
  3. With constraints, mirror about the fixed construction axis line from the SK-06 helper, so Symmetric constraints still apply.
  4. Preview the same way.
- **Possible effects and how to avoid them**
  - Extra construction geometry, as in SK-06. Reuse one line per axis.
  - The axis hit must have lower priority than real curves so lines lying on the axis still win.

## SK-11 (low): stale sketch status and UI state
- **Root cause**
  - "8 sketch entities selected" is a transient message from Ctrl+A (`SketchModeTools.cpp:515`). Delete (`SketchModeTools.cpp:428-429` → `SketchSession.cpp:306`) clears the selection but posts no message.
  - Old tool messages (for example Extend's "Nothing to extend to") survive a tool switch: `SketchTool::activate` (`SketchToolBase.cpp:165`) does not clear the message.
  - Polygon Sides box: `updateValueVisibility` anchors it at the sketch origin until the first click (`CreateTools.cpp:1174-1175`).
- **Fix**
  1. Delete posts "Deleted N entities", or clears the message.
  2. `SketchTool::activate` clears the previous message with an empty Info `showMessage`, after checking how the host treats empty text.
  3. Anchor the Sides box at the cursor in `mouseMove` while `pts_` is empty, and at the centre after the first click.
- **Possible effects and how to avoid them**
  - Complements G1 DOC-08 (status bar, `MainWindow.cpp`). If an empty message is not a clean clear, ask G1 for a `clearMessage` instead of editing `MainWindow` from G4.
  - Tools that show a message inside `activate` (for example "Select a dimension to edit") must clear first and post after.

## SK-12 (low): a finished sketch shows no profile shading
- **Root cause**
  - Shading of finished sketches is gated by `SceneOptions::showProfiles`, which is on only while a tool picks profiles (`viewer/SceneModel.h:79`, `SceneModel.cpp:257`; set in `ViewerWidget.cpp:653`).
  - The in-sketch shading (`SketchSession.cpp:427`, on by default) is not used after Finish.
- **Fix**
  - Draw profiles of visible finished sketches with a lighter, non-pickable style when not picking. Follow the Sketch Palette "Show Profile" state, or a display setting.
  - This lives in viewer files (G3 owns the ViewerWidget display drawer), so implement it with G3. On the G4 side, `SketchFeature::regions()` is already cached.
- **Possible effects and how to avoid them**
  - Profile faces could take clicks meant for bodies or faces behind them. Keep them non-pickable unless a profile-picking tool is active.
  - Draw them with depth offset or transparency so they do not hide coplanar body faces.
  - Region computation is now forced for every visible sketch on load; it is cached per feature, but check load time on large documents.

## SK-13 (low): sketch tools from ux.md missing
- **Plan (new tools, staged)**
  - Slot variants (overall, centre point, 3-point arc, centre-point arc): reuse the SlotTool builder (`CreateTools.cpp:1290+`).
  - Polygon by edge: a third PolygonTool mode, built from the two edge endpoints.
  - Intersect: section the bodies with the sketch plane (`BRepAlgoAPI_Section`), then `projectShape` each edge. This is a new mode of ProjectTool (`ModifyTools.cpp:737`).
  - Defer (they need a 3D sketch, a rational conic or a tangent-handle data model): conic curve (could be a degree-2 rational spline later), include 3D geometry, project to surface, and spline fit-point tangent/curvature handles.
- **Possible effects and how to avoid them**
  - New tool ids and icons appear in the ribbon, toolbar and command search. ToolbarModel and Ribbon belong to G2, so only register tools with group CREATE and let G2 place them.
  - Avoid new shortcut letters.
  - Projection tests in test_feature.
