# G1 fix plan: document lifecycle, tabs, save/dirty state, drawing sheets, timeline, status bar

Status: plan only, not implemented. Sources: docs/tests/general/round1/general-bugs.md and app-tools.md, plus a code read.
General rule: G1 owns core/Document.cpp, core/UndoStack.cpp and core/Commands.cpp. G2 parameter fixes call the existing Document parameter API, and G1 does not change that API. Keep each fix in its own commit so it can be reverted alone. Run the app, core and drawing headless tests (test_main_window, test_app_logic, test_scripting, test_drawing_tools, core tests) after each fix.

## DOC-01 (medium): closing the Design tab while a Drawing tab is open skips the save prompt
- Root cause: in `src/app/MainWindow.cpp:549` (`closeTab`), the prompt runs only when `tab->documentPtr().use_count() == 1`. The Drawing tab shares the same `shared_ptr<Document>`, so the Design tab closes silently. Also, `use_count` is a fragile test: any other holder of the pointer suppresses the prompt.
- Fix: count the open tabs on this document (`std::count_if(tabs_, &t->document()==&doc)`) instead of reading `use_count`. When the tab being closed is the document's Design tab, treat the close as closing the whole document: call `maybeSave` once, then close that document's Drawing tab(s) as well. The recommended reason is that a drawing without its design cannot be edited. The alternative is to prompt and still keep the drawing open. Ctrl+W goes through the same `closeTab`.
- Effects and how to avoid them:
  - Closing the drawing tabs inside `closeTab` re-enters `activateTab` and `destroyTab`. Collect the tabs first, then close the non-active ones before the active one.
  - `setWorkspace(Design)` from a drawing that has no design tab (`MainWindow.cpp:1168`) keeps working.
  - When the last tab of the document closes, `clearRecoveryFile` must still run once per document.
  - Headless (`interactive_ == false`) `maybeSave` returns true, so scripted tests are not affected.
  - Add a test: Design and Drawing tabs open, document dirty, close the Design tab, expect both tabs gone (and the prompt path hit).

## DOC-02 (medium): the Browser dock stays missing after closing the Drawing tab
- Root cause: `MainWindow.cpp:480-487`. The dock is shown or hidden only when `previous && previous->isDesign() != tab->isDesign()`. When the last tab (a Drawing tab) closes, `closeTab` calls `destroyTab` then `addDesignTab()` with `active_ == nullptr`. `previous` is then null, so the dock is never restored.
- Second cause: `closeEvent` (`MainWindow.cpp:1496`) calls `saveState()` while the drawing is active. This stores the hidden dock, and `restoreState` at startup (`:135`) brings it back hidden.
- Third cause: no menu entry re-shows the dock.
- Fix:
  - In `activateTab`, decide visibility from the new tab alone: a Design tab gets `setVisible(browserDockWanted_)`, a Drawing tab hides the dock after remembering the wanted state, and only when the previous tab was a Design tab or there was none.
  - Before `saveState()` in `closeEvent`, show the dock again if `browserDockWanted_` (or save the wanted flag separately).
  - Add checkable "Browser" and "Timeline" entries (`dock->toggleViewAction()`) to the app (hamburger) menu built around `MainWindow.cpp:294`.
- Effects and how to avoid them:
  - The user closing the dock with its x must still stick across Design tabs, so keep `browserDockWanted_` as the source of truth.
  - The Timeline dock already follows `tab->isDesign()`, no change there.
  - The ToolbarModel/Ribbon menu is G2's; the menu entry goes only in MainWindow's own app menu, not in the Ribbon.

## DOC-03 (medium): Sheets panel, sheet tabs and canvas out of sync after undo of a sheet deletion; "-" deletes the wrong sheet
- Root cause:
  - `DrawingSnapshotCommand::undo` calls `DrawingModel::fromJson` (`src/drawing/DrawingModel.cpp:983-1000`), which emits `sheetsChanged`, `activeSheetChanged` and `sheetChanged` back to back.
  - `DrawingWorkspaceWidget::refreshSheets` (`src/drawing/DrawingWorkspaceWidget.cpp:185-212`) rebuilds synchronously, guarded only by `refreshing_`. A re-entrant call during the rebuild (for example list or tab signals, or the canvas switching sheets through `setSheet`, then `setActiveSheet`) is dropped, not deferred. That leaves 2 items, a stale QTabBar with scroll buttons, and the canvas on another sheet.
  - The canvas (`DrawingCanvas::onSheetsChanged`) keeps its old `sheetId_` while that sheet still exists, but the model's `activeSheet_` was restored to the undone sheet.
  - Wrong delete: `onRemoveSheet` (`:242`) runs `drawing.delete-sheet`. `DeleteSheetTool` (`src/drawing/tools/ViewTools.cpp:227`) deletes `activeSheet(ctx)`, which is the canvas's `sheetId()` from `DrawingWorkspaceWidget::forDocument` (the most recently created widget). It is not the row selected in the panel, so after the desync it deletes Sheet1.
- Fix:
  - Make `refreshSheets` coalesced and deferred (a pending flag plus `QTimer::singleShot(0)`, never dropped).
  - Rebuild under `QSignalBlocker` on `sheetList_` and `tabs_` instead of the `refreshing_` flag, then call `tabs_->update()`.
  - Make the model the single source of truth: after a rebuild, if `canvas_->sheetId() != model_->activeSheet()->id`, call `canvas_->setSheet(model active)`.
  - `onRemoveSheet` passes the selected sheet id explicitly. `DeleteSheetTool` accepts a sheet id or name argument (`ctx.args`), or the widget first activates the selected sheet before running the tool.
- Effects and how to avoid them:
  - `test_drawing_tools.cpp:575-580` (new-sheet then delete-sheet with no args) must still delete the active sheet, so keep the no-argument behaviour.
  - The deferred refresh means tests that read the panel right after a model edit need `QCoreApplication::processEvents()`. Alternatively, expose `refreshSheetsNow()` for tests.
  - Drawing tools live outside the G1 file list (`drawing/tools`). The `ViewTools.cpp` change is a one-line argument parse and does not clash with G2, G3 or G4.

## DOC-04 (low-medium): a failed Save renames the document to the failed filename
- Root cause: `MainWindow::saveTo` (`MainWindow.cpp:1465-1466`) calls `document_->setName(stem)` before `Document::save` succeeds. `setName` also calls `touchModified`.
- Also, `saveAs` stores `file/lastDir` (`:1450`) before the save, so the failed folder becomes the next default. The "bad path" the tester saw comes from this. `filePath_` itself is only set on success (`src/core/Document.cpp:916`).
- Fix: remember `oldName` and `oldModified`. On failure, restore them with `setName(oldName)` then `setModified(oldModified)`. Move `s.setValue("file/lastDir")` after a successful `saveTo`. The name must still be set before `save()`, because `toJson` writes the root component name.
- Effects and how to avoid them: the restore emits `nameChanged` twice, which only refreshes the tab and browser, harmless. Autosave and recovery do not use `saveTo`. Add a test: save to `/proc/nope/x.fcad`, expect the name unchanged and the modified flag unchanged.

## DOC-05 (low-medium): suppressing a sketch does not affect or flag the dependent Extrude; Extrude builds from a failed sketch
- Root cause: in `Document::recompute` (`src/core/Document.cpp:363-401`), a suppressed feature gets status `Ok "suppressed"`. Dependents only check `d->status() == Error`, and even then they still run `recompute` and keep the result (status Warning). Extrude reads the sketch's stored curves directly, so it still builds.
- Fix: before `f.recompute(ctx)`, walk the direct feature references, meaning `f.dependencies()` that are features. Do not include body-touch dependencies, because `dependenciesOf` adds every feature that touched a body.
  - If a direct input feature is suppressed, or is in Error with no valid output, skip this feature: `bodyStatesAfter_ = state`, status Error, message "input 'Sketch1' is suppressed" or "input 'Sketch1' failed".
  - Keep today's Warning for inputs that are only Warning.
- Effects and how to avoid them:
  - Restricting the check to direct feature refs avoids false errors, such as a Chamfer on a body that a suppressed Fillet also touched.
  - Errors cascade down the chain (Fusion behaves the same). Assembly joints already skip suppressed features (`JointFeature.cpp:52`).
  - G3 features (Pattern, Fillet, Thread) need no change.
  - Check core and part tests that expect Warning with "has errors". The grep found only `Document.cpp` itself.
  - `reportNewFailures` will now announce the dependent's error as well. That is intended and is covered by DOC-08.

## DOC-06 (low): timeline drag reorders a feature before its producer without validation
- Root cause: validation exists (`TimelineWidget.cpp:162,185` calls `Document::canMoveFeature`, `Document.cpp:131`). However, `NewComponentFeature` (`src/assembly/JointFeature.h:135`) only references its component id. `Document::dependenciesOf` (`Document.cpp:298`) resolves feature ids and body ids only, so a component ref yields no producer and the move of "Body2" ahead of the Extrude is allowed.
- Fix: in `dependenciesOf`, when a dependency id is a component, add the features before `idx` that created or touched bodies now owned by that component (reuse `featuresTouchingBody` for each body with `body->component == dep`).
  - Alternative: give `NewComponentFeature` an `extraDependencies()` listing the bodies it moved in. That would touch assembly files owned by G3's AssemblyModule area, so prefer the core-only change.
  - Also check the move across the rollback marker (`moveFeature` adjusts `rollback_`): the tester saw everything turn stale. Verify that the drop gap left of the marker is not mapped to a marker change.
- Effects and how to avoid them:
  - `dependenciesOf` is also used by `dependentsOf`, the delete plan (`planDelete` "these later features use it") and recompute warning propagation. Component-owned bodies will add more dependents to delete warnings, which is acceptable.
  - Joint features reference components too, so moving a joint before the feature that creates the component's body becomes forbidden. That is correct, but run the assembly tests (`test_assembly_features`).
  - Performance is O(features x bodies) per call, fine at the current scale.

## DOC-07 (low): undo of a body deletion renames Body1 to Body2
- Root cause: `Document::takeFeature` (`Document.cpp:124`) erases the created Body records (name, colour, material, visibility, component). On undo, `RecomputeContext::createBody` (`src/core/Feature.cpp:198-207`) recreates the record with `doc_.uniqueBodyName()`, a fresh name. While the delete macro is undone in reverse, the other bodies still exist, so the number shifts.
- Fix: `RemoveFeatureCommand` (`src/core/Commands.cpp:35-47`) snapshots the `Body` records of `f->createdBodies()` in `redo()`. In `undo()` it re-adds them with `addBody` (same id) before `recompute`, so `createBody` finds them and keeps the name and attributes.
- Effects and how to avoid them:
  - `addBody` emits `bodyAdded` before the shape exists, so the viewer and browser see a body with no shape for one recompute. They already handle missing `currentState_`.
  - Paste/PasteNew (G3) also uses `takeFeature`. The change sits in the command, not in `takeFeature`, so G3 is unaffected.
  - Add a test: delete the body, undo, expect the name and colour kept.

## DOC-08 (low): stale error text in the status bar after the cause is undone or a new command starts
- Root cause: `MainWindow::reportNewFailures` (`MainWindow.cpp:1096-1116`) only ever shows new failures and never clears. `showMessage` text lives for 9 s through `messageTimer_` (`:373`) whatever happens. "Unknown command: foobar" comes from CommandLine and is cleared the same way.
- Fix:
  - Remember the last failure message (`lastFailureMsg_`). In `reportNewFailures`, when `now` is empty or no longer contains that feature, clear `messageLabel_` if it still shows that text.
  - In `runCommand`/`onToolActivated`, clear a lingering Error or Warning message before the tool's `activate()` runs. Clear before, never after, so a message the tool itself shows on activate ("select a face first") survives.
- Effects and how to avoid them: `test_main_window` and `test_scripting` read `messageText()` right after an error, and that order is unchanged. Clear only messages that this code itself posted (compare the text). G4 SK-11 handles sketch tool prompts, and G2 touches CommandLine, so leave CommandLine untouched and clear only from MainWindow.

## DOC-09 (low): dirty markers out of sync after save, or after redo back to the saved state
- Root cause: `BrowserTree` builds the root label "name *" (`src/app/BrowserTree.cpp:297`) but only rebuilds on `nameChanged` and similar signals, never on `modifiedChanged` (`:95-111`). Separately, `Document::modified_` is set by `touchModified` and is independent of `UndoStack::cleanIndex_`. Redo or undo back to the clean index never clears it.
- Fix:
  - In BrowserTree, connect `Document::modifiedChanged` to update only `topLevelItem(0)->setText` (no full rebuild, which keeps expansion state).
  - In the `Document` constructor, connect `undo_->cleanChanged(bool c)` to `setModified(!c)`.
  - In `UndoStack::push`, when a command merges into the top command while `cleanIndex_ == index_`, set `cleanIndex_ = -1` (the merge path at `src/core/UndoStack.cpp:28-31` skips this).
  - Wherever a document is made dirty outside the stack (recovered file `MainWindow.cpp:793`, `setModified(true)` after load), mark the stack "never clean" with a new `UndoStack::resetClean()` that sets `cleanIndex_ = -1`, so a later undo cannot falsely clear the flag.
- Effects and how to avoid them:
  - Order is safe: commands touch modified first, then `setIndex` emits `cleanChanged`.
  - Non-undoable edits (drawing `notifyChanged`, `setExtensionData`) still mark dirty. An undo to the clean index would then clear the flag, a small false-clean risk. Mitigate by having `touchModified()` outside an undo or redo set `cleanIndex_ = -1` (add a `UndoStack::isApplying()` flag).
  - Tests that check `isModified()` after undo to the initial state will now see false (the intended behaviour). Update `test_app_logic` expectations if any exist.
  - BrowserTree is shared with G2 (APP-04 type-ahead). This is a separate connect line, so merge carefully.

## DOC-10 (low): new documents all called "Untitled"; a new Drawing is dirty and shows a blank page with an empty Sheets panel
- Root cause: `Document::clear()` and the constructor always use "Untitled" (`Document.cpp:60`), and `newDocument` (`MainWindow.cpp:1316`) does not rename. The drawing tab (`setWorkspace` to `openDrawingTab`, `:1163`) opens with no sheet. Nothing calls `drawing.create`, so the page and panel are empty. The dirty flag on open is not yet located. Candidates are `DrawingModel::addSheet` or `notifyChanged` through a tool's `activeSheet(ctx, create=true)` (`DrawingToolBase.cpp:122`), or `setExtensionData`. Confirm with a breakpoint on `Document::setModified(true)`.
- Fix:
  - In `MainWindow::newDocument` and `addDesignTab` for a fresh doc, name it "Untitled", "Untitled 2", and so on, using the lowest number not used by an open tab.
  - Add `core::isAutoDocumentName(name)` (regex `^Untitled( \d+)?$`) and use it in `DocumentTab::isPristine` (`DocumentTab.cpp:93`) and `MainWindow` `:1416` and `:1465`.
  - When the drawing has no sheets, show an empty state in `DrawingWorkspaceWidget` with a "Create Drawing" button that runs `drawing.create` (the Fusion "Create Drawing" dialog). An explicit user action may then mark the document dirty. Merely opening the drawing must not.
- Effects and how to avoid them:
  - Tests asserting `name()=="Untitled"` (test_main_window, test_app_logic, test_assembly_features, StepExport fallback) must keep passing. Keep `Document` defaulting to "Untitled" and number only in MainWindow, so core tests are unaffected.
  - Recovery file names change with the doc name, which is harmless.
  - `isPristine` must treat "Untitled 2" as pristine, or opening a file would leave empty tabs behind.

## DOC-11 (low): tab strip repaint glitch after dragging a tab
- Root cause: `tabMoved` (`MainWindow.cpp:253-258`) only reorders `tabs_`. During a drag, `refreshTabBar()` (`:526`, triggered by `modifiedChanged`, autosave or state refresh) calls `setTabText` by index while QTabBar is animating, which produces duplicate labels and a stale current-index indicator.
- Fix:
  - After the reorder, defer one `QTimer::singleShot(0)` that runs `refreshTabBar()`, `tabBar_->setCurrentIndex(indexOfTab(active_))` under `switchingTabs_`, and `tabBar_->update()`.
  - Skip `refreshTabBar` while a drag is in progress (`QGuiApplication::mouseButtons() & Qt::LeftButton` with the pointer over `tabBar_`) and set a pending flag that runs on release.
- Effects and how to avoid them: `findTab` uses numeric indices from `tabs_`, which stays consistent. The `switchingTabs_` guard stops `currentChanged` from re-activating tabs. A test can simulate the reorder with `tabBar_->moveTab(0,1)` and check the texts match `tabs_`.

## DOC-12 (low): marking menu label truncated; timeline item stays framed after Cancel
- Root cause, marking menu: the fixed `kSlotW = 120` (`src/app/MarkingMenu.cpp:19`), with elision at `:98`, cuts "Repeat Rectangle".
- Root cause, timeline: the frame is `TimelineStrip::highlighted_` (`src/app/TimelineWidget.cpp:52`). It is set on timeline select or double-click edit (`MainWindow.cpp:971`) and by `scrollToFeature` (`:322`), and is never cleared when the edit command is cancelled or the selection changes.
- Fix, marking menu: in `popup`, compute the slot width from `fontMetrics().horizontalAdvance` of the longest radial label, clamped to 120-170 px. Widen `rx` and `kSize` to match, or shorten the label to "Repeat: Rectangle" with eliding of the middle part only.
- Fix, timeline: in `onToolFinished`, clear the highlight (`setHighlightedFeature(kInvalidId)`) unless the feature is still selected. Also connect the doc selection `changed` signal so the highlight clears when the feature leaves the selection.
- Effects and how to avoid them: hit-testing in `slotAt` is angle-based, so wider slots do not change picking. Check that diagonal slots do not overlap at the larger width (`slotRect` ellipse factors). "Find in timeline" relies on the highlight staying, so clear it only on a tool finishing or a selection change, not on a timer.
