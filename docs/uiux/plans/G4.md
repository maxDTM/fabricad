# G4 fix plan: commands, browser, workspaces (UX-32..UX-43)

Status: plan only, nothing is implemented yet. It is based on reading the code and the round-1 findings and screenshots. Line numbers refer to HEAD 2026-10-22.

## Ground rules for the whole group
- Do not touch src/viewer/*, MainWindow.cpp, Ribbon.cpp, ToolbarModel.cpp, the QSS or resources/icons (G1/G2). Where one of those is needed, it is listed under "needs G1" or "needs G2".
- **Chair regression guard.** docs/comparison/fabricad/chair_min.fcs (and chair.fcs) uses EXTRUDE, NEWCOMPONENT, CFB, `SELECT component:<name>`, MOVECOMPONENT, GROUND (multi-select), DELETECOMPONENT and RENAME. src/part/tests/test_chair_split.cpp builds MoveBody features directly. After every G4 change, run ctest plus the chair script, and diff the result against chair_min.log (body count, volumes, exported STL).
- Build with -j2 only.

## UX-32 (high): Move/Copy has no triad and ignores viewport picks
- Root cause:
  - No manipulator provider is registered for MoveBody. FeatureManipulators.cpp:429-449 `installBuiltins` has no `MoveBodyFeature::kType`, so only the FeatureValueBox for the primary numeric ("X distance") appears.
  - `FeatureTool::onManipulatorEvent` (FeatureTool.cpp ~294) maps one gizmo to one property through `e.value`. It cannot drive dx/dy/dz/rx/ry/rz from a single Triad.
  - Viewport picks fail because of G1 UX-02. The browser pick works (`selectionChanged` -> `addRefToInput`).
- Fix:
  - Add `moveBodyManipulators`. It returns one `ManipulatorKind::Triad` placed at the pivot: the bbox centre of the selected bodies in the state before the feature, or px/py/pz. Handles are `kHandleMoves|kHandlePlanes`, plus `kHandleRotations` when moveType is Free. Use the property "dx" as the binding key.
  - In FeatureTool, add a Triad branch:
    - On DragBegin, snapshot dx..rz.
    - On Drag, set start + `e.value` on the property chosen by `e.handle`: MoveX->dx, ..., RotZ->rz. Plane handles set two properties from `e.delta.TranslationPart()`.
    - On DragEnd, refresh the panel.
  - Make "Free Move" the default moveType for new Move features (Fusion's default), so the rotation rings are live. Set it in `applyDefaultsForNewFeature`, not in the constructor, so loaded files and test_chair_split keep the values they set.
  - Also show the moved preview body. It already comes from `outcome_.previews`. Check it after G1 UX-01 lands.
- Possible effects:
  - Triad scale and size: copy MoveComponentTool's `setupTriad` sizing (pixelSize) so the two triads look the same.
  - The `primaryNumeric()` value box still anchors on "dx" through `manipulatorFor`. That function looks up `handlePoint(None)`, which for a Triad is the centre, so the box sits on the triad. Offset it, or anchor on the MoveX tip.
  - The old Translate default is still reachable through the combo and `moveType=` on the command line. The `MOVE 10` command-line argument still sets dx.
  - Picking acceptance can only be verified after G1 UX-02. If picks arrive as Face/Edge on a body, `addRefToInput` rejects them (filter = Body). Body priority is applied by the viewer (G1); no G4 change is needed unless the viewer reports sub-shapes.

## UX-33 (medium): Box Length/Width/Height ignore typed values
- Root cause: not confirmed.
  - PropertyPanel.cpp:176-189 already applies the value on `textEdited` (delay 0 for new features) and on `editingFinished`. `refresh()` (:121) skips a focused edit.
  - The strongest lead is key routing. Tester note: "only the on-canvas Height box was editable; the final size did not match". This matches keys going to `ToolManager::keyPress` -> `FeatureValueBox::keyPress` (FeatureValueBox.cpp:104), which consumes digits for the primary numeric (Height). That happens when `MainWindow::isCanvasFocus()` (MainWindow.cpp:1440) gets `QApplication::focusWidget()==nullptr`. That is likely on the rootful Xwayland test display with no window manager or active window: `!focus` returns true, so the key is treated as a canvas key.
- Fix:
  1. First write a QTest (src/part/tests). Run part.box, `QTest::keyClicks` into `prop_length`, press Tab, and assert the property and the preview. This tells a G4 bug apart from a routing bug.
  2. G4 guard: in `FeatureTool::keyPress`, return false when the focus widget, or the receiver, is inside `panel_`. Do the same in `FeatureValueBox::keyPress`.
  3. Needs G2: in `MainWindow::eventFilter`, pass the receiver `w` when `focusWidget()` is null, so a key aimed at a QLineEdit is never treated as a canvas key.
  4. Keep the commit on `editingFinished` and Tab. After the commit, `updatePreview` already runs. Also call `valueBox_->update` so the canvas box shows the new Height.
- Possible effects:
  - Step 2 could swallow Enter/Esc while a panel field has focus. Let only printable and Tab keys through to the field; Enter/Esc must still reach the router (OK/Cancel).
  - The sketch value boxes (G3) use the same ValueInputOverlay. Do not change the overlay.

## UX-34 (medium): Edit Feature shows no live extrude preview and the body disappears
- Root cause:
  - In edit mode, `updatePreview` (FeatureTool.cpp ~370) recomputes the real document, so the body itself should be the live preview. Screenshots 51/52 show the arrow moving (15 -> 30), but no Body1.
  - The most likely cause is the viewer dropping the old presentation and not redrawing the new one (G1 UX-01).
  - Second candidate: `rollbackToFeature` plus the recompute leaves the body with a null shape for one frame, and the scene never re-syncs.
- Fix:
  - Re-test after G1 UX-01.
  - If the body is still missing, show a transient preview in edit mode from `editing_->outputShape()` (or `outcome_.previews` of a dry compute against `bodyStatesAfter(idx-1)`), drawn with `styleFor(op)`. Hide the real body with `setFeatureVisibilityOverride(editingId, false)` while the tool runs, and restore the visibility in `accept`/`cancel`/`deactivate`.
  - Keep the 150 ms debounce (`setValueChangeDelay(editing_ ? 150 : 0)`).
- Possible effects:
  - Overrides must always be restored, or bodies stay hidden after Esc or a tool switch. Clear them in `deactivate()`, which every path reaches.
  - Recompute cost doubles if both the preview and the real recompute run. Use one or the other.

## UX-35 (medium): undo has no effect on assembly operations; Move/Ground add no timeline entry
- Root cause:
  - The commands already exist. `makePlacementsCommand` (ComponentOps.cpp:232) is pushed by `MoveComponentTool::accept` (:427). `makeGroundCommand` is pushed by `setGround` (ComponentTools.cpp:225-231). CFB is a macro of `CreateComponentCommand` with timeline markers.
  - So "nothing changes visibly" is most likely G1 UX-01: the viewer does not redraw after `componentChanged`/`bodyChanged`. Placement undo only emits `notifyComponentChanged`.
  - Move and Ground produce no Feature, so the timeline never changes.
  - Bug: CreateComponentCommand redo after undo creates a new component id. A later "Move component" command then refers to the old id and silently does nothing (redo chain CFB -> Move -> undo x2 -> redo x2).
- Fix:
  - Add a headless test (test_assembly_tools): CFB x2, Move, Ground, undo x3, then assert placements, grounded flags, component count and feature count. Run it before changing anything.
  - Timeline: add an assembly `PositionFeature` (type "Position", icon "move"). It stores {componentId: placement} after the move and applies them in `recompute()`, so rolling back before it restores the old placement. MoveComponentTool::accept pushes AddFeatureCommand(Position) in a macro with the placements command.
  - Ground: keep it a component flag (Fusion does not time-stamp Ground), but make the result visible with the pin from UX-36. Flag for human review whether a "Ground" marker feature is really wanted.
  - Fix the stale-id redo by remapping ids in the placements command. Use `remapComponentIds`, or key placements by a stable component name/uuid.
- Possible effects:
  - Joint solving (`recomputeJoints`) and Position features both set placements. Apply Position before the joints in the recompute order, or skip components that are jointed.
  - DeleteComponentCommand (ComponentOps.cpp:401-430) must drop or rehome Position features that reference the deleted component. `referencesComponents` already scans refs; store the ids as refs so this works. The chair script deletes LegFrame after moving other components.
  - File format: the new feature type needs registration in AssemblyModule and JSON round-trip tests. Old files are unaffected.
  - The chair script's MOVECOMPONENT x3 will add 3 timeline features. Feature counts in chair_min.log and any test asserting `doc.features().size()` change; update them deliberately.

## UX-36 (medium): assembly context menus incomplete, no ground pin, component naming
- Root cause:
  - BrowserTree.cpp:434-500 `contextMenuEvent`. The Body branch has only material/appearance. The component Ground action (:463) pushes `makeComponentEditCommand` directly, which bypasses `assembly.ground` (status message, `recomputeJoints`).
  - There is no grounded decoration. The only grounded marker is the tooltip at :248.
  - The root "Bodies" folder is always added (:176 `|| root`).
  - CFB names the component after the body (ComponentTools.cpp:274).
- Fix:
  - Body menu: "Create Components from Bodies" (`emit runToolRequested("assembly.components-from-bodies")` with the selection) and Isolate.
  - Component menu: route Ground/Unground through `runToolRequested("assembly.ground"/"assembly.unground")`; add Isolate (new `app.isolate`/`app.unisolate` tool: a macro hiding every other body/component, undoable through `toggleVisibility`).
  - Keep Properties.
  - Pin: set the column-0 icon to `assembly-ground.svg` (already in resources/icons) for grounded components, or overlay it on the component icon.
  - Hide the root Bodies folder when it is empty and the root has child components.
  - Naming: **keep CFB naming the component after its body.** Fusion does this ("Body1:1"), and the chair script relies on `SELECT component:LegLeft` after CFB. Show the occurrence suffix ":1" in `componentLabel` for every non-root component. An empty New Component stays "ComponentN" -> "Component1:1".
- Possible effects:
  - Changing `componentLabel` affects every caller: the status bar, BOM and drawings, and tests comparing labels. Add the suffix only in the BrowserTree display, or make it an option. Selectors must still match the bare name and should also accept "Name:1".
  - Inline rename must edit the bare name, not "Name:1". Set the editor text from `c->name` in `onItemRenamed`.
  - Hiding the root Bodies folder breaks drop targets and the eye-folder logic in `folderVisible`. Check `setFolderVisible("Bodies")` callers.

## UX-37 (medium): parts list shows only Body1 and overflows the sheet
- Root cause:
  - `DrawingModel::bom(view)` (DrawingModel.cpp:469) passes the base view's sources. The base view took the preselection (ViewTools.cpp:254-256; status "active Body1"), so `buildBom` restricts to Body1.
  - In the assembly branch, `restrictedTo` (Annotations.cpp:207) never matches Body sources (bodyId = kInvalidId), so rows depend on how the view was made.
  - The table width is the fixed sum of `columnWidths`. Nothing clamps it to the frame (SheetRenderer.cpp:351 `addPartsList`; the placement tool does not check the border).
- Fix:
  - A parts list lists the whole design: `bom(nullptr)` unless the view sources are explicit Components (Fusion lists the top-level assembly of the referenced design).
  - In `restrictedTo`, map a Body source to its component chain.
  - On placement and on refresh, shift the table left/up so `pos + width/height` stays inside the sheet border minus the margin. If it is still too wide, scale the column widths down to fit, with a minimum font size.
- Possible effects:
  - Balloons use `bomItemFor(rows)`, built from the first parts list. Item numbers change when rows are added; recompute the balloons (refreshAnnotations already does).
  - CSV export (DrawingExport.cpp:145) shares `bom()` and gains the same rows. That is intended; update its tests.
  - Saved drawings with a parts list re-layout on load. That is acceptable, because the position is clamped and not lost.

  - In sketch/62 the boxed "Sketch2" row may be the current-item focus frame from QSS (G2) and not a QLineEdit.
- Fix:
  - Reproduce with a QTest: double-click a sketch row, then assert `state() != QAbstractItemView::EditingState`.
  - If an editor really opens: set `NoEditTriggers` (F2 is handled in `keyPressEvent` :581 and the menu calls `editItem` explicitly), and override `mouseDoubleClickEvent` to consume the event for feature rows.
  - If it is only the focus frame: needs G2 (QSS `QTreeView::item:focus`/outline). Optionally call `clearFocus()` / `setCurrentItem(nullptr)` when sketch edit starts.
- Possible effects:
  - With `NoEditTriggers`, an explicit `editItem()` still works (Qt allows it), so F2, the menu and timeline rename (MainWindow.cpp:778) keep working.
  - Double-click on a body/component still renames (line 72). Fusion's double-click on a component activates it; leave that unchanged in this round, but list it for review.

## UX-39 (low): SELECT menu has no window/freeform/paint modes, no filters, no active check
- Root cause: AppTools.cpp:273-295 registers only the priority tools. `ToolInfo` (core/Tool.h) has no checked state; the ribbon menu (Ribbon.cpp, G2) cannot show one.
- Fix:
  - Add tools select.window / select.freeform / select.paint. They set a viewer drag mode through an existing ViewerContext API; rectangle select exists in G1 (`rectangleSelect`). Freeform and paint are disabled until G1 provides them.
  - Add "Selection Filters" toggle tools (one per kind group). They AND a user mask into `SelectionModel::setFilter`, kept separate from the tool filter.
  - Add an optional `std::function<bool()> checked` (plus `exclusiveGroup`) to `ToolInfo` in core/Tool.h. Priority tools return `v.selectionPriority()==p`.
  - Needs G2: Ribbon/ToolbarModel render checkable, exclusive actions.
- Possible effects:
  - Adding a field to `ToolInfo` changes a core struct used everywhere. Use a default-initialised member so aggregate/designated initialisers (`.name = ...` in ComponentTools.cpp:43) still compile.
  - User filters must not combine with tool filters in a way that blocks a tool's pick. Reset them or ignore them while a tool with its own filter runs; FeatureTool::applyFilter overwrites the filter today.

## UX-41 (low): marking menu offers "Repeat 2-Point Rectangle" during Extrude
- Root cause: MarkingMenuModel.cpp:47-58. While a tool is active, NE = repeat of `ctx.lastToolId`, which is the last sketch tool.
- Fix: in the `toolActive` branch, drop the repeat (OK/Cancel/Undo plus fit/look-at is the command context). Outside a sketch, ignore a `lastToolId` whose `info().tab == "SKETCH"` (or `id` starts with "sketch."), so Repeat names the last solid command. That last command is stored in the ToolManager; it is not available inside the model.
- Possible effects: src/app/tests/test_app_logic.cpp asserts the marking menu content; update it. Pressing Enter to repeat (`repeatLast`, MainWindow) is unaffected, because only the menu entry changes.

## UX-42 (low): consumed sketch stays visible after Extrude (the origin-plane half is G1 UX-10)
- Root cause: `FeatureTool::accept` (FeatureTool.cpp ~600-640) does not change sketch visibility. The persistent hide (`setFeatureHidden`) is only on ViewerWidget and not on `core::IViewerContext`.
- Fix:
  - Add `setFeatureHidden(id, bool)` to `IViewerContext` (core/ViewerContext.h; ViewerWidget already implements it, so it only needs `override`; the headless stub at ViewerContext.h:226 needs a no-op).
  - After a new Extrude/Revolve/Sweep/Loft/Rib commit, hide the owner sketch of every profile ref (`ref.owner` -> the sketch feature id). Do not hide it on Edit, and do not hide a sketch that is still in use as an active profile elsewhere.
  - Do not use `setFeatureVisibilityOverride`. It is a temporary override that would block the browser eye from showing the sketch again.
- Possible effects:
  - The hide is not undoable. Undoing the extrude leaves the sketch hidden; Fusion behaves the same, but note it.
  - Hidden sketches may become unpickable in the viewer. Textual selectors (chair script `SELECT profile...`) do not use visibility; check `Selectors.cpp:477 profilesOf`.
  - The interface change touches the G1-owned ViewerWidget.h (one `override` keyword). Ask G1 to add it.

## UX-43 (low): drawing annotation collisions, lingering cyan views, "View of View" status
- Root cause:
  - The dimension text offset ignores existing section-line labels (AnnotationTools.cpp, default dimension offset).
  - Views stay in the canvas *selection* (kSelectColor, DrawingCanvas.cpp:163) after the parent-view pick: projected/section/detail tools add the picked parent to the selection, and `detachCanvas` clears only the highlights (DrawingToolBase.cpp:182).
  - The status text comes from AppState.cpp:160: `kindLabel + " of " + ownerName` gives "View of View" for a DrawingView ref.
- Fix:
  - When placing a dimension, test the text bbox against the section-label and view-label bboxes of the sheet, and push the text outward by one text height until it is clear.
  - In `deactivate`/finish of the view tools, clear the canvas selection if the tool put the parent there.
  - In AppState, add a case for drawing kinds that returns the view label ("View 2 (Front)" / "Section A-A").
- Possible effects: AppState.cpp is shared (not in any group's list); G4 takes it. Moving the dimension text changes the PDF export layout; update the drawing export tests' golden values if any exist.
